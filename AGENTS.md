# AGENTS.md — notification-service

Single-module Spring Boot 4.1.1 / Java 21 / Maven service (`com.fardorado.notification`). Kafka ingestion, subscription matching, webhook delivery and database-backed retries are implemented (features 001 + 002) behind a hexagonal architecture; requirements and C4 design live in `docs/spec/`, and `README.md` covers building, running and configuring the service.

## Commands

- No Maven wrapper (`mvnw` absent) — use the system `mvn`.
- Run app: `mvn spring-boot:run`
- All tests: `mvn test` — requires a reachable Docker daemon (Testcontainers). On Windows where Docker lives inside WSL2, use `.\scripts\run-tests.ps1` (or `./scripts/run-tests.sh`) instead; it passes every argument through to Maven.
- Single test class: `mvn test -Dtest=NotificationServiceApplicationTests`
- Single method: `mvn test -Dtest=NotificationServiceApplicationTests#contextLoads`
- Package: `mvn package`

## Critical context

- **Feature 002 status: code-complete, integration tests never executed against a real daemon.** The event-processing pipeline compiles and its 50 unit tests pass, but on this Windows machine every `*IntTest` fails at `Could not find a valid Docker environment` (see Docker bullet below). The full runbook — including the tier-by-tier list of *likely integration-test failures and their fixes* — is `docs/spec/features/002_EventProcessingComponents_implementation_plan.md` §3. The 002 changes were uncommitted in the working tree as of the last session.
- **Known latent bug to fix first: Jackson 2 injections in the 002 adapters.** `KafkaNotificationConsumer` and `WebhookChannelClientImpl` inject `com.fasterxml.jackson.databind.ObjectMapper` as a Spring bean. Per the Jackson 3 rule below there is no such bean, so the Spring context will fail at startup once Testcontainers are reachable (on the Linux machine this is the *first* failure to expect). Migrate them to the auto-configured Jackson 3 `tools.jackson.databind.json.JsonMapper` before anything else. Unit tests that construct `new ObjectMapper()` themselves are fine.
- **Tests need Docker.** `TestcontainersConfiguration` starts a PostgreSQL container (`postgres:latest`) and a Kafka container (`apache/kafka:latest`) via `@ServiceConnection`; `mvn test` fails without a *reachable* Docker daemon. The first run pulls both images (slow). Unit tests alone: `mvn test -Dtest='!*IntTest,!NotificationServiceApplicationTests' -DfailIfNoSpecifiedTests=false`.
- **Docker may need `DOCKER_HOST` — and on this Windows machine it still isn't enough.** Docker runs as a native daemon inside the `Ubuntu` WSL2 distro (unix socket only). `scripts/run-tests.{ps1,sh}` hold the distro open for the whole run (WSL2 stops an idle distro and takes the daemon with it, mid-run) and set `DOCKER_HOST` to the `docker-tcp-proxy` socat bridge using the first address of `wsl -d Ubuntu -- hostname -I` as a literal IPv4, never `localhost` (the JVM may resolve `localhost` to `::1`). Even with all of that correct, Testcontainers' docker-java client still dies on streaming/keep-alive requests through the bridge with `NoHttpResponseException` (short requests succeed; the same pulls work from inside WSL and from a plain JDK `HttpClient`). Net: **run `*IntTest` suites on the Linux machine with native Docker**; on this Windows machine treat integration tests as unrunnable and rely on the unit-test subset.
- **Jackson 3, not Jackson 2.** Spring Boot 4 auto-configures `tools.jackson.databind.json.JsonMapper`. Jackson 2 (`com.fasterxml.jackson.databind`) is on the classpath only transitively and has **no bean**, so injecting its `ObjectMapper` compiles and then fails at startup with `No qualifying bean of type 'com.fasterxml.jackson.databind.ObjectMapper'`. Annotations stay in `com.fasterxml.jackson.annotation`.
- **`windows-unixdomain-tmpdir` profile in `pom.xml`.** On Windows setups where security software holds `%TEMP%`, the AF_UNIX socket behind `Selector.open()` cannot be connected to, and anything selector-based (JDK `HttpServer` test stubs, Kafka clients, Testcontainers) dies with `Unable to establish loopback connection`. The profile redirects `jdk.net.unixdomain.tmpdir` to `target/`. Do not "simplify" it away; `-Djava.io.tmpdir` is not an equivalent, since `UnixDomainSockets` reads the `TEMP` environment variable.
- **Per-technology starter pattern.** The pom uses `spring-boot-starter-webmvc`, `spring-boot-starter-webmvc-test`, `spring-boot-starter-data-jpa-test`, `spring-boot-starter-kafka`, and `spring-boot-resttestclient`. Follow this pattern when adding dependencies.
- **`TestRestTemplate` moved in Boot 4, and needs two extra things.** It lives in `org.springframework.boot.resttestclient` (artifact `spring-boot-resttestclient`), not in Boot 3's `org.springframework.boot.test.web.client`. It is also **no longer auto-registered** for `RANDOM_PORT`: the test class must be annotated `@AutoConfigureTestRestTemplate`, or the context fails with *No qualifying bean of type 'TestRestTemplate'*. And it is built on `RestTemplateBuilder`, which is **not** pulled in transitively, so `spring-boot-restclient` must be a test dependency too, or the context fails with `NoClassDefFoundError: org/springframework/boot/restclient/RestTemplateBuilder`. No REST integration tests exist yet; apply this recipe when adding them.
- **No `(:param is null or ...)` in JPQL against PostgreSQL.** Optional filters written that way make Postgres fail with `could not determine data type of parameter $N`, because the null bind is untyped. Build optional filters as a Spring Data `Specification` instead, so an unsupplied filter never reaches the SQL.
- **Lombok is wired manually.** Annotation processing is configured via `annotationProcessorPaths` in `maven-compiler-plugin` (both `default-compile` and `default-testCompile`, together with MapStruct + `lombok-mapstruct-binding`). Adding another annotation processor means editing both executions in `pom.xml`.

## Event-processing pipeline (feature 002) — where things live and how it behaves

- Flow: `adapter/in/messaging/KafkaNotificationConsumer` → `ProcessNotificationEventUseCaseImpl` (idempotent via `findByEventId`; no active subscription → event persisted directly as `FAILED`) → `adapter/in/scheduler/NotificationEventDispatchScheduler` (`@Scheduled`, gated by `notification.processing.dispatch-enabled`) → `DeliveryClaimService` (one `@Transactional`: `FOR UPDATE SKIP LOCKED` claim + transition to `DELIVERING` + new append-only `delivery_attempt`) → bounded virtual-thread worker pool → `ProcessDeliveryUseCaseImpl` (webhook call **outside** any transaction) → `DeliveryResultService` (second `@Transactional`: attempt result + `COMPLETED`/`RETRY_SCHEDULED`/`FAILED` per `RetryPolicy`). Stale `DELIVERING` events (lease exceeded) are recovered by the claim step, never silently completed.
- `notification_event.updated_at` doubles as the stale-delivery lease timestamp — the claim query treats `updated_at <= now - lease-timeout` as stale. Stale-recovery tests backdate it via JDBC.
- **Integration-test conventions:** persistence IntTests set `notification.processing.dispatch-enabled=false` so the scheduler doesn't race test assertions; `EventProcessingFlowIntTest` enables it with fast properties (poll 200ms, backoff 100ms, lease 2s). Each Kafka IntTest class deliberately uses its **own topic** (`notification-events-ingestion-test`, `notification-events-flow-test`) because the consumer group is shared across cached Spring contexts — don't "deduplicate" them.
- Sample broker events are consumed verbatim as test data from `src/test/resources/sample/notification_events.json` (a copy of `docs/spec/sample/notification_events.json` — keep in sync). In that file `delivery_date`/`delivery_status` are metadata, not ingested fields; `event_version`/`correlation_id` are optional (default 1 / null).
- Plain-text `content` is wrapped as `{"content": "..."}` before persistence because the `payload` column is JSONB; structured JSON content is stored verbatim. This mapping lives in the Kafka consumer (adapter), not the use case.

## Mandatory rule docs (already loaded via `opencode.json` → `docs/ai/rules/*.md`)

Read before writing any code — these are enforced conventions, not suggestions:

- `ARCHITECTURE_CONVENTIONS.md` — hexagonal architecture (ports & adapters). Dependencies point inward: adapter → application → domain. Domain has zero Spring/JPA/Kafka/Jackson dependencies. Separate `Notification` (domain) from `NotificationEntity` (persistence).
- `NAMING_CONVENTIONS.md` — suffix rules: `*UseCase`/`*UseCaseImpl`, `*RepositoryImpl`, `*JpaRepository`, `*Controller`/`*ControllerImpl`, `*IntTest`, `*RequestDto`/`*ResponseDto`, `*Command`, `*Result`, `*Entity`; the `Jpa` infix is reserved for `*JpaRepository` only; no `Rest` prefix on controllers; domain services are plain classes (no interface + impl pairs).
- `PROJECT_GUIDELINES.md` — integration tests run the full Spring context (`RANDOM_PORT`, `TestRestTemplate`, Testcontainers), never MockMvc. Controllers are interfaces carrying the OpenAPI docs, with implementations in a sibling `impl` package. Layer mappers are MapStruct.

## Stack notes

- Messaging: Kafka (`spring-boot-starter-kafka`), consumer with manual ack (`manual_immediate`); the broker message is acknowledged **only after** durable persistence. Poison messages (malformed/invalid) are logged and acknowledged so they can't block the partition — a deliberate, documented decision.
- Persistence: PostgreSQL. Liquibase owns the schema (`src/main/resources/db/changelog`, three tables: `subscription`, `notification_event`, `delivery_attempt` — deliberately no `deliveries` table) and `ddl-auto` is `validate`, so entity/column mismatches fail at startup. The v1.0 changesets were rewritten **in place** for schema corrections before any environment had ever executed them — that exception is spent; from now on, schema changes require new versioned changesets.
- REST layer: not implemented yet (next feature). When added: springdoc-openapi 3.1.0, controller interfaces in `adapter/in/web` with OpenAPI annotations, `*ControllerImpl` in the sibling `impl` package, `advice/GlobalExceptionHandler` → `ErrorResponseDto`.
- **REST client identity is the `X-Client-Id` header.** There is no Spring Security in this project; the header stands in for the authenticated principal, and ownership is enforced by the use cases (via `notification_event.subscription_id -> subscription.client_id`), never by the controller. A missing header is a 401. Never add a `client_id` query parameter.
